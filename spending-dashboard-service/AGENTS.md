# AI Usage Record

AI assistance was used to scaffold and implement this Spring Boot spending dashboard application-layer deliverable. The generated plan, project structure, domain records, transaction-source interface, in-memory source, constructor-injected application services, console runner, tests, and evidence notes were reviewed against the assignment requirements.

The implementation was checked for the Lesson 5 handoff boundary: both use cases depend on `TransactionSource`, the original transaction-source interface and application services remain unchanged, and the transaction-query service preserves source order without sorting again. The code was also reviewed for BigDecimal money handling, immutable values, null/blank/identifier validation, and absence of controllers, field injection, setter injection, service lookup, and source construction inside services.

AI assistance was also used to add the JPA/PostgreSQL spending data source deliverable. The generated JPA entities for `users`, `accounts`, `merchants`, `categories`, and `transactions` were mapped from `spending_dashboard_schema.sql`; `spending_insights` and `parent_category_id` hierarchy mapping were kept out of scope. The Spring Data repository uses a JPQL monthly dashboard query scoped through `transaction -> account -> user`, a half-open date range, deterministic ordering, and fetch joins for required to-one references. `JpaTransactionSource` adapts entities into the existing application `Transaction` values inside a read-only persistence boundary, while `InMemoryTransactionSource` is active only under the `in-memory` profile.

Verification was performed with the checked-in Gradle wrapper and portable Java 21. Successful `./gradlew test` results, seeded PostgreSQL repository evidence, and the SQL-log excerpt are recorded in `evidence.md`.

AI assistance was also used to add the Spring Security JWT authentication boundary deliverable. The generated web/security dependencies, `user_auth_credentials` schema extension, BCrypt credential exchange, startup-generated RSA JWT signing keys, access/refresh token services, current-refresh-token digest persistence, stateless resource-server configuration, protected caller probe, HTTP tests, decisions, and evidence notes were reviewed against the deliverable requirements. Verification used runtime-generated synthetic test credentials only; no plaintext password, password hash, reusable bearer token, token signature, refresh-token digest, or private key was recorded in source evidence.

AI assistance was also used to add the Lesson 7 versioned Transaction API deliverable: an OpenAPI-first `/api/v1` REST surface over the existing Lesson 5/6 spending services and authentication boundary. The generated work — `openapi/openapi.yaml` (declaring `openapi: 3.2.0`, bearer security, reusable `Money`/`ProblemDetail`/`TransactionType`/`TransactionDirection` schemas, and the three required operations with stable `operationId`s), `DashboardController`, `TransactionController`, `InsightStreamController`, the write-side `TransactionCreationService` and its `AccountJpaRepository`/`MerchantJpaRepository`/`CategoryJpaRepository` collaborators, the `CreatedTransaction` application record, `ApiExceptionHandler`'s RFC 9457 Problem Details mapping, the `spring-boot-starter-validation` addition, the shared `JwtTestSupport`/`OpenApiContractSupport` test helpers, and `TransactionApiHttpTest` — was reviewed against the deliverable's exit criteria (L7-1 through L7-8).

The review specifically checked: every financial operation derives identity only from `Jwt#getSubject()` and never trusts a caller-supplied user id (verified by an identity-isolation test showing one user's token cannot read or write another user's data); the dashboard and transaction-create controllers delegate to application services, and `TransactionCreationService` converts its saved entity to `CreatedTransaction` before returning so `TransactionController` has no JPA-entity import or access; the existing `MonthlySummaryService`/`MonthlyTransactionQueryService`/`TransactionSource` ordering contract is unchanged and reused as-is; the insight stream emits only hard-coded, deterministic text across multiple SSE chunks with no LLM SDK, API key, prompt, or call to any model, and writes nothing to the unmapped `spending_insights` table; and money is represented as decimal strings end-to-end so `BigDecimal` values round-trip exactly. The existing Lesson 6 test sources were left unmodified.

One tooling gap was found and resolved during verification, not before: the Java OpenAPI-parsing libraries resolvable from Maven Central (swagger-parser 2.1.22 and its swagger-request-validator consumers) do not yet recognize `openapi: 3.2.0` and silently fall back to a legacy Swagger 1.x parser. Rather than downgrade the checked-in contract's declared version to fit older tooling, `OpenApiContractSupport` was rewritten to validate response bodies structurally against the contract's `components.schemas` using a version-agnostic JSON Schema validator; full 3.2.0 spec compliance is verified separately by `npx @redocly/cli lint`, which supports 3.2.0 and passes with zero warnings. See `DECISIONS.md` for the full rationale.

Verification used the checked-in Gradle wrapper, a portable Java 21 toolchain, and Testcontainers PostgreSQL. Results are recorded in `evidence.md`, including `./gradlew test`, the Redocly lint output, an authenticated dashboard read, a transaction creation with its `Location` header, a multi-chunk SSE capture, an identity-isolation result, representative Problem Details output, and the schema-based contract checks (including one error response and the SSE media type). No bearer token, password, or other secret is recorded in source evidence.
